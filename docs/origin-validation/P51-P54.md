# Open Fufu — Origin Validation Coverage P51–P54

## Status and authority

This file is a continuation of [`../ORIGIN_VALIDATION_COVERAGE.md`](../ORIGIN_VALIDATION_COVERAGE.md) and uses the same canonical coverage model.

It owns **validation coverage/dependency tracing only** for P51–P54. Origin mechanics remain canonical in [`../ORIGIN_TRAIT_CATALOGUE.md`](../ORIGIN_TRAIT_CATALOGUE.md), and focused subsystem mechanics remain owned by their normal documents.

The relationship classes remain:

1. **Direct transformation** — the subsystem whose rule/value/permission/state the trait directly changes.
2. **Required integration seam** — trait-specific state/event flow crossing subsystem boundaries.
3. **External semantic dependency** — canonical state/mechanics the trait reads but does not own.
4. **Ordinary downstream consumption** — valid canonical state that ordinary consumers must already handle without redundant trait-specific implementations.

Explicit interactions include same-Origin interactions, cross-system interactions, and cross-faction Origin interactions where appropriate. Mechanic-definition holes discovered here are blockers only; this file must not invent the missing gameplay rule.

# 1. P51–P54 coverage

## P51 — One Flag Beneath the Stars

**Direct transformations / owners**

- Persistent Command Post effective support field as consumed by land-combat defensive-pressure composition.
- Every **owned active Command Post** additionally projects defensive pressure equal to that Command Post's effective offensive-pressure magnitude across the Command Post's existing effective coverage.

**Required seams / dependencies**

- `owned active Command Post completed level -> effective Command-Post offensive-pressure magnitude + effective coverage -> P51 defensive field -> defended target-cell qualification -> final lane defensive pressure`.
- P51 uses the Command Post's **effective offensive profile magnitude** as the defensive-bonus source; it must not look up an unrelated hidden baseline when another explicit transformation changes that effective profile.
- The projected defensive pressure modifies the effectiveness of an actual ordinary defender; it must not manufacture an automatic defender on an otherwise undefended cell.
- Same-type overlapping Command Posts continue to use the baseline strongest-applicable same-type rule rather than stacking several P51 fields.
- P51 applies from Command Posts owned by the holder as stated canonically; it must not silently broaden to teammate-owned Command Posts unless a future mechanic explicitly says so.

**Cross-type composition requirement**

- P51 does **not** require P50 in order to overlap another structure-derived defensive field. An ordinary Fort already projects defensive pressure, while P51 makes a Command Post project defensive pressure.
- Where an ordinary/effective Fort defensive field and a P51 Command-Post defensive field both affect the same engagement, their distinct cross-type bonuses use the catalogue's complement rule:

```text
combinedBonus = 1 - (1 - A) × (1 - B)
```

- Same-type strongest-field handling is still resolved before/within the normal structure-field pipeline; the complement rule is for the distinct Fort and Command-Post field types rather than permission to stack every overlapping structure.

**Explicit interactions**

- `P51 + P50`: explicitly legal reciprocal support. P50 adds Fort-derived offense while P51 adds Command-Post-derived defense. Where both structure types contribute to the same pressure direction, use the same cross-type complement rule; selecting both does not create a third bespoke combination formula.
- `P51 + P03`: P03 removes hostile **Fort-derived defensive pressure** for attacks by the P03 holder. It must not remove P51 Command-Post defensive pressure merely because both participated in one combined defensive result. Coverage should include an engagement where the Fort component is filtered while the Command-Post component remains.
- `P51 + P09`: P09 changes effective Fort coverage/magnitude, so it changes the Fort component that may overlap P51 defense without changing P51's Command-Post source rule.
- `P51 + N08`: when N08 removes Fort defensive pressure, a qualifying P51 Command-Post defensive field remains independently meaningful; N08 must not zero the Command-Post-derived component.
- `P51 + N10`: N10 changes where the Fort component exists, so it changes which cells require Fort+P51 complement composition.
- P13 and other terrain/Origin defensive effects may share the final pressure calculation, but ordinary multi-source pressure-composition coverage is preferable to pair-testing every unrelated defensive modifier.

**Non-effects**

- P51 does not create defenders, alter Command-Post cost/level/ownership, make Command Posts autonomously attack, or modify Tank/Warship/strategic-weapon damage.

## P52 — Humanity Has Declined

**Direct transformations / owners**

- Cross-domain Population-state -> FFY-economy transformation.
- Adds one global non-spatial passive FFY source based on the holder's current unused Population Capacity:

```text
emptyCapacity = max(0, PopulationCapacity - TotalPopulation)
P52BonusFFYPerSecond = emptyCapacity / 250
```

- The source never becomes negative and consumes no Population.

**Required seams / dependencies**

- `current authoritative Population Capacity + current Total Population -> emptyCapacity -> P52 passive FFY source -> ordinary global/general FFY modifier/accounting pipeline`.
- P52 must read the **current** authoritative values rather than snapshotting Capacity or Population at spawn. Territorial gain/loss, Population growth/loss, explicit Population transfers, and other ordinary state changes naturally change the subsequent source value.
- `TotalPopulation >= PopulationCapacity` must produce exactly zero P52 income rather than a negative FFY source.
- P52 is classified as a global/general FFY source for modifier eligibility. It must not accidentally inherit Military/conquest, Naval/trade, Industrial, or spatial-event modifiers merely because those systems also produce FFY.
- Tick accumulation/rounding must be deterministic under the ruleset's ordinary passive-income representation; fractional per-second values are a numeric implementation concern rather than permission to change the authored formula.

**Explicit interactions**

- `P52 + P48`: direct same-Origin state dependency. P48 changes which owned Shallow-Water cells contribute Capacity; P52 must consume the resulting faction-effective Capacity immediately rather than a globally hard-coded terrain classification.
- `P52 + P01`: P01 changes Initial Territory/starting Capacity and Starting Population together. P52 must begin from the resulting canonical initialized values rather than compute from the ordinary 1,000/500 baseline.
- `P52 + P02`: explicitly legal and potentially strong, but the mechanics remain separated: P02 changes Population growth over time, while P52 reads the resulting current Population/Capacity state. This is ordinary state propagation rather than a special combined formula.
- `P52 + P33`: P33 Population grants can reduce empty Capacity; P52 must reflect the new Total Population after the canonical Population event resolves without requiring a P33-specific economy implementation.
- `P52 + P42`: successful Population-funded Warship purchases permanently reduce Total Population and therefore can increase later P52 income. This is ordinary Population-state propagation, not a refund or Warship-purchase rebate.
- Cross-faction Population/Capacity mutations such as territorial loss, P44 neutralization, or P47 casualties likewise feed P52 only through the resulting canonical state; they do not require bespoke P52 interaction formulas.

**Non-effects**

- P52 does not modify Population growth, Capacity itself, territorial acquisition, purchase prices, event values, or FFY losses. It is one passive source derived from already-authoritative Population state.

## P53 — Money Is Everything

**Direct transformation / owner**

- P53's passive-income formula and persistent-Silo-only eligibility are canonical in `ORIGIN_TRAIT_CATALOGUE.md`.
- This validation document does not restate the formula or the persistent-Silo charge lifecycle.

**Required seams / dependencies**

- `owned active persistent Missile Silo -> canonical READY-slot projection -> P53 passive FFY source -> ordinary global/general FFY modifier/accounting pipeline`.
- The READY-slot projection, initial activation state, spending transition, upgrade-created capacity behavior, capture preservation, and serialized deadlines are consumed directly from `TERRAIN_AND_STRUCTURES.md`.
- Strategic launches consume the charge transition defined by `NAVAL_AND_STRATEGIC_WEAPONS.md`; P53 observes the resulting persistent-Silo READY count rather than implementing launch state itself.
- P53's source remains global/general for FFY modifier eligibility; it must not accidentally become a spatial, Military/conquest, Naval/trade, or Industrial event.

**Required exclusions / interactions**

- `P53 + P20`: verify the admitted P20 Silo enters the ordinary newly materialized persistent-Silo lifecycle and P53 immediately consumes the resulting READY projection.
- `P53 + P26`: a zero-FFY MIRV does not waive ordinary launcher-charge consumption; P53 observes the resulting persistent-Silo state if that launch used a persistent Silo.
- `P53 + P29`: verify mobile Warship launcher charges never enter P53's persistent-Silo input.
- `P53 + SAM`: verify SAM charges never enter P53's persistent-Silo input.
- `P53 + N07`: ownership caps may change which persistent Silos legally exist, but do not change P53's formula or bypass admission.

**Resolved mechanic-definition result (#46)**

- #46 closes the external persistent-Silo charge-state dependency in `TERRAIN_AND_STRUCTURES.md`; P53 no longer needs validation metadata to choose a readiness rule.

**Required scenario coverage after #46**

- `P53_COUNTS_READY_PERSISTENT_ONLY`: income follows the canonical READY projection, not capacity or historical launches;
- `P20_USES_ORDINARY_NEW_SILO_STATE`: a successful starting grant exposes the same initial charge state as another newly materialized completed Silo;
- `SILO_UPGRADE_PRESERVES_OLD_SLOTS` and `SILO_UPGRADE_NEW_SLOT_RECHARGES`: P53 observes the resulting READY count without inventing an upgrade exception;
- `SILO_CAPTURE_PRESERVES_DEADLINES`: ownership transfer preserves physical charge state and P53 for the new owner consumes that state;
- `P53_EXCLUDES_P29` and `P53_EXCLUDES_SAM`: structurally similar charge projections never broaden the authored persistent-Silo eligibility;
- save/reload/replay reproduces the same P53 input transitions on the same ticks.

## P54 — Starlight Breaker

**Direct transformation / owner**

- Spawn generated Initial-Territory **geometry only**, in Strategic, Random, and Fixed modes.
- Replaces ordinary compact candidate priority with canonical `P54_STAR_V1` star-shape priority while preserving the faction's final population-bearing Initial-Territory quota.
- `P54_STAR_V1` is an immutable Q12-style integer template with map-north orientation, clockwise winding, ten explicitly enumerated vertices, and template SHA-256 `52318cc016a674164fc4861468e29b24b177b8fc35287337a55a11d1b6773440`.

**Required seams / dependencies**

- `Origin effective spawn profile -> footprint shape = STAR -> exact rational P54 candidate scoring -> simultaneous connected frontier resolver -> final political ownership -> Population initialization`.
- The star template is a **priority field**, not a guaranteed polygon/eligibility mask. Runtime construction remains cardinally connected and cell-by-cell through the ordinary footprint resolver.
- Barriers, coastlines, Deep Water, Impassable terrain, topology, and foreign footprint contests may deform or eliminate individual ideal arms. The resolver must continue through progressively higher-score legal frontier cells elsewhere until quota is filled whenever reachable legal geography exists.
- No hard star-radius cutoff may reduce quota, and no disconnected painting may rescue a blocked arm.
- Population-bearing claimed cells consume quota; legally claimed owner-effective `0 Capacity` cells do not. Faction-effective population-bearing classification must therefore be consumed exactly as in ordinary/P39 footprint resolution.
- Foreign-faction cell collisions remain ordinary simultaneous Spawn collisions; P54 must not create shape-specific execution-order priority.
- Replay/snapshot binds `spawnResolverVersion`, `P54_STAR_V1`, the canonical template SHA, final realized cell IDs, and cell-set SHA-256.
- Identical map/profile/exact-origin inputs must produce the same realized P54 footprint regardless of whether that exact origin came from Strategic, Random, or Fixed Spawn.

**Exact geometry validation obligations**

- Recompute the canonical template serialization and require SHA-256 `52318cc016a674164fc4861468e29b24b177b8fc35287337a55a11d1b6773440`.
- Reproduce every canonical Section 5.2 edge/`N`/`D` golden vector from `STRATEGIC_SPAWN.md` using exact integer/rational comparison.
- Verify vertex-ray edge-selection convention, including the `v0` ray selecting edge `0` rather than edge `9`.
- Reject any implementation that regenerates authoritative vertices through runtime trigonometry or rounds/quantizes `N/D` before candidate comparison.
- Verify resolver-v1 `stableTie32Id = FNV1A32_LENPREFIX_V1` and its canonical Section 3.1 golden vectors before certifying final P54 cell-set hashes.
- Full realized fixture cell-set hashes are published by executable Spawn certification once a concrete canonical map/`CellId` fixture and executable Spawn resolver harness exist. The resolver-v1 `stableTie32` primitive is already frozen in `STRATEGIC_SPAWN.md`; the remaining unavailability is fixture/runtime, not tie semantics.

**Explicit interactions**

- `P54 + P39`: explicitly legal. Each P39 split footprint uses an independent `P54_STAR_V1` field around its stable origin slot; one total faction quota is still split between the two footprints, and Starting Population remains one global pool.
- `P54 + P01`: P01 modifies the final quota while P54 changes only geometry. The resolver consumes farther into the same priority field to reach the P01-modified target rather than changing the template.
- `P54 + P48`: if a P48 footprint legally claims Shallow Water, owner-effective population-bearing classification controls whether that claimed cell consumes quota, exactly as for compact/P39 footprints. P54 does not get a separate hard-coded terrain table.
- `P01 + P39 + P54` remains not builder-legal under the current positive-spend limit, so no public same-Origin runtime certification case is required for that triple.

**Ordinary downstream consumption / non-effects**

- The realized footprint may expose more ordinary actionable neutral/contact boundary, but later acquisition geometry, settlement cost, capture speed, land pressure, and Population allocation remain ordinary mechanics. They do not become P54-specific runtime systems after spawn completes.
- P54 does not alter exact-origin terrain legality, final Initial Territory, Starting Population, Capacity per cell, neutral-settlement Population cost, or later territorial-growth shape.

**#32 closure status**

- Random/Fixed semantics are closed: P54 applies after exact-origin resolution in all three spawn modes; Fixed authored origins fix location rather than suppressing the shape mechanic.
- Resolver-v1 geometry is closed: the exact integer template, serialization/hash, winding/orientation, exact rational score, vertex-ray tie convention, and cell-by-cell deformation semantics are canonical in `STRATEGIC_SPAWN.md`.
- P54 no longer has a mechanic-definition blocker under #32. Runtime certification may remain `UNAVAILABLE` until the concrete Spawn resolver/test fixture exists, but it is not `BLOCKED` on undefined P54 semantics.

# 2. P50 coverage correction discovered by P51

The earlier P50 trace remains directionally correct but one composition obligation should be made explicit:

- P50 does **not** require P51 for cross-type offensive-field composition. A baseline Command Post already projects offensive pressure; P50 makes a Fort additionally project offensive pressure. Therefore a P50 Fort overlapping an ordinary Command-Post offensive field must already use the catalogue's Fort+Command-Post complement rule.
- P51 creates the reciprocal case on defense: an ordinary Fort defensive field overlapping a P51 Command-Post defensive field uses the same complement rule.
- `P50 + P51` makes both reciprocal directions active at once; it does not introduce a different third formula.

This clarification should be preserved when the final interaction registry is consolidated.

# 4. Positive-trait audit conclusions

With P01–P54 traced, several validation boundaries are now strongly evidenced rather than hypothetical:

- **Spawn / pre-match initialization** — spawn profiles, quota, faction-relative population-bearing classification, starting grants, deterministic geometry/replay.
- **Population state/accounting** — initialization, Capacity, growth, peak state, settlement costs/residuals, casualties/transfers, state-derived passive effects.
- **Land combat / capture resolution** — pressure composition, counter-response, capture casualties, post-capture effects, structure-derived fields.
- **Terrain / territorial mutation** — acquisition modifiers, Fallout overlays, abandonment, faction-relative terrain classification, build permissions.
- **Persistent structures / transactions / lifecycle** — purchase/upgrade/grant actions, provenance, caps/entitlements, structure effective profiles and charge state.
- **FFY economy / physical logistics** — source families/modifier ordering, Train/Trade lifecycle, event-driven side effects, Population/charge-derived passive sources.
- **Naval / amphibious lifecycle** — Warship/Transport profiles, movement, repair, rank/caps, landing/destruction interactions.
- **Strategic weapons / interception** — launcher legality, charge state, projectile/blast geometry, SAM interception/anti-ship behavior.
- **Observation / concealment** — lawful reveal/blackout projection, terrain- and structure-derived concealment, manifestation exceptions.

Cross-system seams and explicit interaction cases remain first-class validation obligations; the final taxonomy should still wait until N01–N18 are traced because negative traits may reveal additional hard-prohibition/admission boundaries.
